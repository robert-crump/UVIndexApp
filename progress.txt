## Issue #19 — Wind data flows into the forecast

### Status: COMPLETE

### Parent
#18 — Wind widget (1x1). This is Slice 1 of 2 (data path + direction math);
Slice 2 (#20) builds the 1x1 WindWidget on top of it.

### What was implemented

**`OpenMeteoApi.kt`:**
- Extended the default `hourly` query from `uv_index,temperature_2m` to
  `uv_index,temperature_2m,windspeed_10m,winddirection_10m`. Open-Meteo's default
  `windspeed_unit` is `kmh`, so no unit param is needed — the issue's "km/h" is the default.

**`WeatherResponse.kt` (`HourlyData`):**
- Added `@SerialName("windspeed_10m") windSpeed: List<Double> = emptyList()` and
  `@SerialName("winddirection_10m") windDirection: List<Double> = emptyList()`. Defaulted to
  empty so a partial/legacy API response without the fields still deserializes.

**`UVForecast.kt` (`HourlyForecast`):**
- Added `windSpeed: Double = 0.0` (km/h, rounded) and `windDirection: Double = 0.0`
  (source bearing in degrees — where the wind comes FROM). **Defaults are load-bearing**:
  `CachedWeatherData` serializes `UVForecast`, so old cached payloads written before this
  change still deserialize (the back-compat acceptance criterion).

**`WeatherRepository.parseWeatherResponse()`:**
- Populates the two new fields per hour: `windSpeed` via
  `response.hourly.windSpeed.getOrNull(index)?.roundToInt()?.toDouble() ?: 0.0` (rounded at
  parse time, same pattern as uv/temperature from #10/#15), `windDirection` via
  `response.hourly.windDirection.getOrNull(index) ?: 0.0` (kept raw; bucketed to an octant by
  the display helper, so no rounding needed). `getOrNull` guards against the empty-list default.
- `reParseWithCurrentTime()` needed no change — it copies `HourlyForecast` objects straight
  from `allDayForecasts`, so wind survives the cache re-parse for free.

**New pure module `com.uvindex.app.wind.WindDirection`
(`app/src/main/java/com/uvindex/app/wind/WindDirection.kt`):**
- `enum class CompassOctant { N, NE, E, SE, S, SW, W, NW }` — ordered clockwise from North;
  ordinal == 45° octant index.
- `fun travelOctant(sourceBearingDegrees: Double): CompassOctant` — converts the
  meteorological source bearing into the octant the wind travels TOWARD:
  `travel = source + 180`, normalized into `[0,360)` (handles negative / >360 inputs),
  then `(travel / 45).roundToInt() % 8` indexes `CompassOctant.entries`. So a wind "from N"
  (0°) yields a southward arrow. Pure Kotlin, no Android imports — used by Slice 2's widget.

**`WindDirectionTest.kt` (`app/src/test/java/com/uvindex/app/wind/`):**
- 11 pure JVM tests: 4 cardinal sources (N→S, E→W, S→N, W→E), 2 intercardinal (NE→SW, SW→NE),
  2 rounding-boundary cases (22°→S, 23°→SW), and 3 normalization cases (350° wrap, exactly
  360°, negative −90°).

### Notes / not done

  the method is private and `WeatherRepository` has no DI seam (same constraint noted for
  #15/#10). The direction math — the actual risk in this slice — is fully covered by the pure
  `travelOctant` tests. The data threading is verified by a clean compile + green suite.

## Issue #16 — Long loading times

### Status: COMPLETE

### Root cause
`LocationService.getCurrentLocation()` called `fusedLocationClient.getCurrentLocation()`
(`requestFreshLocation()`) with no timeout. On the reported run the fused provider hung
for 20+ seconds before the app could even check the cache, so the loading spinner stayed
up the whole time — and once it returned, the location had moved enough (or enough time
had passed) to also trigger a background refresh, which is why the displayed
`lastUpdateTime` jumped from 06:48 → 07:02 without a manual pull-to-refresh.

### What was implemented
**`LocationService.kt`:**
- Added `FRESH_LOCATION_TIMEOUT_MS = 5_000L` and wrapped `requestFreshLocation()` in
  `withTimeoutOrNull(...)`. If the fused provider doesn't answer within 5s, we fall back
  to `getLastKnownLocation()` immediately (same fallback chain as before, just bounded).
  `withTimeoutOrNull` cancels the inner coroutine on timeout, which triggers the existing
  `continuation.invokeOnCancellation { cancellationTokenSource.cancel() }`, so the
  in-flight fused-location request is properly cancelled rather than left running.

### Test results
`:app:testDebugUnitTest` — all existing tests pass (no LocationService unit tests exist,
as `FusedLocationProviderClient` is a final Play Services class that isn't practical to
fake without a larger DI refactor; the fix is a minimal, localized timeout).

## Issue #1 — Location change not recognized (background worker)

### Status: COMPLETE

### Root cause
Background workers (WidgetUpdateWorker, HourlyUpdateWorker, periodic updates) all
refresh data via `WeatherRepository.getUVForecast()`, which calls
`LocationService.getCurrentLocation()`. That method only used
`FusedLocationProviderClient.getCurrentLocation(PRIORITY_BALANCED_POWER_ACCURACY)`,
which in the background frequently resolves to null (or failed and threw). On null,
`WeatherRepository.getUVForecast()` falls back to the *stored old coordinates*
(WeatherRepository.kt:48-54) and re-fetches the OLD city — so a >15km move was never
detected by any background worker. The CacheManager 15km threshold was fine; the
workers simply never had a fresh location to compare. It only self-corrected when the
user opened the app (foreground fix succeeds), matching the reported "~9 hours" and
"opening the app fixed it" symptom. The stale widget "(city)" label was the visible
side effect of the stale cached forecast.

### What was implemented
`LocationService.getCurrentLocation()` now falls back to the device's last known
location before giving up:
- `requestFreshLocation()` — the original `getCurrentLocation(...)` fresh-fix path,
  but failures now `resume(null)` instead of `resumeWithException` (so a transient
  failure no longer bubbles up and forces the stored-coords fallback).
- `getLastKnownLocation()` — new fallback using `fusedLocationClient.lastLocation`,
  which the system / other apps keep current, so it reflects a real location change.
- `getCurrentLocation()` = `requestFreshLocation() ?: getLastKnownLocation()`.
The repository's stored-coordinates fallback is now a genuine last resort (both fresh
and last-known null). Removed the now-unused `resumeWithException` import.

### Clarification gathered (AskUserQuestion)
- Symptom scope: not sure if numbers were stale; label was wrong.
- Opening the app fixed it → foreground works, background does not.
- Move was to a different city (>15km) → distance threshold not the issue.

### Notes / not done
- `LocationService` wraps a `FusedLocationProviderClient` created in its constructor,
  so there is no unit-test seam; adding one needs a DI refactor (out of scope for this
  single fix). No new test added; existing suite re-run to guard against regressions.
- Pre-existing uncommitted UVWidget.kt label tweak ("UV-Index (city)" -> "city") left
  untouched in the working tree; it is cosmetic and unrelated to this root-cause fix.

## Issue #15 — Consistent Max. UV hour

### Status: COMPLETE

### Root cause
`parseWeatherResponse()` stored raw float UV indices (e.g., 6.1, 5.8, 6.4) in `HourlyForecast.uvIndex`.
The UI and chart displayed them as integers via `.toInt()` (truncation), so 1 PM (UV=5.8→5),
2 PM (UV=6.1→6), and 4 PM (UV=6.4→6) could all show "6" in the diagram — but `maxByOrNull { it.uvIndex }`
found 4 PM as the float maximum and set `maxHourToday = 4`, not 1 PM (the first hour displaying UV=6).
Temperature had already been rounded at parse time since issue #10; UV was not.

### What was implemented

**`WeatherRepository.kt`** — one-line fix in `parseWeatherResponse()`:
- `uvIndex = response.hourly.uvIndex[index].roundToInt().toDouble()`
  (same pattern as the temperature rounding from issue #10; `roundToInt` import was already present).

With rounded values, `maxByOrNull { it.uvIndex }` on tied hours returns the **first** element
(Kotlin's implementation uses strict `<`, so equal values keep the earlier element). This matches
the spec: "if several hours have the same highest UV index, the tile should reflect the first of those hours."

`reParseWithCurrentTime()` reads `allDayForecasts` from cache (which is now stored with rounded values),
so the same guarantee holds for re-parses.

No new tests — `parseWeatherResponse` and `reParseWithCurrentTime` are private and have no JVM-testable
seam without DI refactoring. All 49 existing tests pass (no regressions).
