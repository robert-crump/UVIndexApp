## 2026-09-18 — Issue #31: UV Forecast — remove dead derived fields, solar math and the abandoned clear-sky chart

### Status: COMPLETE

### What was implemented
Removed derived `UVForecast` data that was computed, cached and re-derived on every
read but never surfaced to the user, per the issue's confirmation that the clear-sky
chart is abandoned, not unfinished.

**`data/model/UVForecast.kt`:** removed `clearSkyMax`, `clearSkyHourly` and
`highUVTimeSlots` fields from `UVForecast`; deleted the now-unreferenced `TimeSlot`
data class entirely.

**`data/repository/WeatherRepository.kt`:** removed the `TimeSlot` import and all
computation of the three dead fields from both derivation paths (`parseWeatherResponse`
and `reParseWithCurrentTime`, which lost its now-unused `latitude` parameter). Deleted
the ~130 lines of solar/astronomy math that only fed those fields: `findHighUVTimeSlots`
(UV >= 4.0 threshold, which matched no glossary concept — `classifyUvRisk` owns "High"
at >= 6), `calculateClearSkyHourly`, `calculateSolarElevation`, and
`calculateSolarDeclinationFactor`. The repository now contains no astronomy.

**`ui/components/UVChartComposables.kt`:** deleted `ClearSkyBarChart`, which had no
caller. `UVBarChart` and `TemperatureLineChart` are untouched and still render (used by
`UVChartDialog`/`TemperatureChartDialog` in `UVIndexScreen.kt`).

**`ui/screen/UVIndexScreen.kt`:** deleted `UVChartCard`, which also had no caller (a
separate dead composable from the two dialog-based charts that are still live).

**`test/notification/NotificationDeciderTest.kt`:** the 4 test-fixture functions that
constructed a full `UVForecast` (`fakeForecast`, `forecastWithUV`, `dailyForecast`,
`forecastWithHoursAt`) dropped the 3 removed constructor args each.

Cache-miss safety: `WeatherRepository.getCachedForecast()` already wraps
`json.decodeFromString<CachedWeatherData>` in a try/catch that returns `null` on any
decode failure, which was reused as-is — an old cache with the previous (larger) JSON
shape now fails `kotlinx.serialization` strict decoding (unknown-but-absent required
fields), is caught, logged, and returns `null`, which callers already treat as a cache
miss and fall through to a fresh API fetch. No new code needed for this path, only
confirmed by reading the existing exception handling.

### Notes / not done
- Did not touch the two derivation paths' shared duplication (parse-time vs.
  cache-re-read both recompute `dailyMax`/`nextHours`/etc. independently) — the issue
  explicitly scoped that unification to a future slice.
- No manual on-device install-over-previous-build test performed (no device/emulator in
  this environment); verified the crash-safety claim by code inspection of the existing
  try/catch instead, per the acceptance criteria's own "manual test" caveat.

### Test results
`grep -rn "clearSky\|highUVTimeSlots" app/src` — no matches.
`:app:testDebugUnitTest` — BUILD SUCCESSFUL, all existing tests pass (fixture-only
changes, no new tests needed).
`:app:assembleDebug` — BUILD SUCCESSFUL.

closes the gap. Pre-implementation: used `/grill-me` to resolve scope (1x1 only — no

## 2026-07-29 — Widget redesign: match main-screen UV colors, drop labels

### Status: COMPLETE

### What was implemented
Pre-implementation: used `/grill-me` to resolve the design before writing code — which
widget "3x1" actually referred to (the 4-cell row widget, not a literal 3-cell one),
exactly which text counted as "the label" per widget, whether to reuse the main screen's
`getColorInt` palette instead of the widget-only `getWidgetUVColor`, per-cell vs.
whole-widget backgrounds for the row widget, full-bleed vs. framed background for the
1x1, outer-frame/gap treatment once cells got their own colors, time-caption color, and
the error/no-data visual. Mid-session the user also decided the 1x1 should switch from
showing the daily max to the current-hour UV, which required a full rename since
`AppWidgetProvider` class identity is tied to placed home-screen instances (acceptable
here at `versionCode 1`).

**1x1 widget — renamed `UVWidgetMax` → `UVWidgetCurrent`** (class, layout
`uv_widget_max.xml` → `uv_widget_current.xml`, appwidget-info file, ids, the
`ACTION_REFRESH_MAX` action constant, and `strings.xml`'s `widget_max_description` →
`widget_current_description` = "Aktueller UV-Index"):
- Now reads `forecast.currentHour` instead of `dailyMaxRemaining`/`maxHourToday`.
- Dropped the static "Max." header entirely; kept the bare hour caption (e.g. "14:00").
- Whole widget is now a full-bleed rounded background colored per UV bucket via new
  `widget_bg_{low,moderate,high,very_high,error}.xml` drawables (24dp corners, colors
  pulled from the same `colors.xml` entries the main screen's cards use), swapped at
  runtime with `views.setInt(id, "setBackgroundResource", ...)`. Number and hour caption
  both use `UVColorHelper.getColorInt(..., FOREGROUND)` — the exact main-screen palette.
- Accepted as intentional: this duplicates the row widget's current-hour cell when both
  are placed.

  from the old widget-only `getWidgetUVColor` to `getColorInt(..., FOREGROUND)`.
- Error/no-data cells (both the "-" fallback loop and outer error drawables) use a new
  shared `@color/widget_uv_error_background` (dark neutral gray, `colors.xml`) so a
  broken cell is never mistaken for a real low-UV green reading.

**`SelfProtectionTimeWidget.kt`** (user follow-up after the main change): its value
text also switched from `getWidgetUVColor` to `getColorInt(..., FOREGROUND)`, for the
same reason — consistency with the main screen's UV color, not just the two widgets
originally in scope.

**`UVColorHelper.kt`**: `getWidgetUVColor()` removed — after the `SelfProtectionTimeWidget`
follow-up it had no remaining callers anywhere in the app.

**`WidgetUpdateHelper.kt` / `WidgetUpdateWorker.kt`**: updated their `UVWidgetMax` →
`UVWidgetCurrent` references (class import, broadcast target, log strings); also fixed
a stale "2x2 Max Widget" comment in `WidgetUpdateWorker.kt` to say "1x1 Current UV

**`AndroidManifest.xml`**: receiver entry renamed `.widget.UVWidgetMax` →
