## Issue #27 — Notifications: Multiple fires

### Status: COMPLETE

### Root cause
Reported symptom: two overlapping "high radiation" block notifications the same day, first
"14:00-16:00" (2-4pm), then "15:00-17:00" (3-5pm). `NotificationDecider.worseNews()`
(`NotificationDecider.kt`) re-fires the UV Warning same-day if any High UV Hour at/after `now`
wasn't in the previously-warned `WarnedAbout.highHours` set. As the day progresses, the
upstream forecast reclassifies the now-past hour 14 back below the High threshold (it drops
out of `highHours`) while hour 16 newly crosses into High — the window didn't get longer, it
just slid forward by one hour, but "hour 16 wasn't in the old set" was enough to count as
Worse News and re-fire an effectively-duplicate notification.

### What was implemented
**`NotificationDecider.kt` (`worseNews`):** added a second condition alongside the existing
"new high hour at/after now" check — the current `highHours` set must also be strictly larger
than the previous one (`current.highHours.size > previous.highHours.size`). A pure same-length
forward shift (one hour drops off the front, one appears on the back) no longer re-fires; a
genuine extension (old hours retained, new ones added — window really got longer) still does,
as does a higher peak or an earlier first-high-hour (unchanged, both already independent
`worseNews` branches).

**`CONTEXT.md` (Dedup Rules → Worse News):** updated the "new High UV Hour" bullet to spell
out the size-growth requirement and cross-reference #27, so the doc matches the refined code.

**`NotificationDeciderTest.kt`:** added 3 tests — `worseNews` false for a same-length forward
shift, `worseNews` true when a shift also grows the window, and a `decide()`-level
reproduction of the exact #27 scenario (14-15 → 15-16 at now=15) asserting no re-fire.

### Notes / not done
- Existing `worseNews`/`decide` tests for genuine extension, earlier start, higher peak, and
  shrink were re-verified against the new size condition and still pass unchanged — the fix is
  additive (narrows one branch), not a behavior rewrite.

### Test results
`:app:testDebugUnitTest` — BUILD SUCCESSFUL. 73 tests run, 73 passed (0 failures).
- NotificationDeciderTest: 25/25 passed (22 pre-existing + 3 new)
- All other suites unchanged and green.

## Issue #21 — Widgets not updating after location change

### Status: COMPLETE

### Root cause
Widgets carry no location of their own — they render whatever forecast is in the cache.
The cache is refreshed by `WidgetUpdateWorker`, a *background* WorkManager job (scheduled in
`UVIndexApplication` every 30 min, `WidgetUpdateScheduler` every 15 min, plus screen-unlock).
That worker calls `WeatherRepository.getUVForecast()` → `LocationService.getCurrentLocation()`.
The app declared **only foreground** location permissions (`ACCESS_COARSE/FINE_LOCATION`);
there was no `ACCESS_BACKGROUND_LOCATION`. On Android 10+ a background process is denied
location: the fresh fix returns null *and* the `lastLocation` fallback (#1) is restricted, so
`getUVForecast()` fell back to the **stored coordinates = City A** and re-fetched City A
indefinitely. Only a foreground fix (app open) succeeded — exactly matching the report
("opening the app fixes it instantly; closing it updates the widgets immediately").

There is no way to relocate widgets without opening the app unless the app holds
`ACCESS_BACKGROUND_LOCATION` — an Android permission-model constraint, not a code bug.

### What was implemented
Chosen approach: add `ACCESS_BACKGROUND_LOCATION`, gated behind an explicit **opt-in toggle
in Settings** with a prominent in-app disclosure (best Play-policy posture, lowest UX
intrusion). Existing default behavior is unchanged for users who don't opt in.

**`AndroidManifest.xml`:**
- Added `<uses-permission android:name="android.permission.ACCESS_BACKGROUND_LOCATION" />`
  (auto-granted with foreground on API ≤28; runtime-gated on 29+).

**New pure helper `com.uvindex.app.data.location.BackgroundLocationPermission`
(`app/src/main/java/com/uvindex/app/data/location/BackgroundLocationPermission.kt`):**
- `enum class BackgroundLocationStep { AlreadyGranted, RequestForegroundFirst,
  RequestBackgroundInline, DirectToSystemSettings }`.
- `fun nextBackgroundLocationStep(sdkInt, foregroundGranted, backgroundGranted)` — pure,
  Android-free decision for the multi-step permission routing (background requires foreground
  first; can only be requested via dialog on API 29; API 30+ must be granted in system
  settings). Same extract-pure-logic-and-test-it pattern as `travelOctant` / `classifyUvRisk`.

**`SettingsActivity.kt`:**
- New "Standort" section with one Switch ("Automatische Standortaktualisierung"). The Switch
  mirrors the **real** OS grant state, re-read on every `ON_RESUME` via `LifecycleEventEffect`
  (the user may grant/revoke in system settings), not a stored bool.
- Toggling on shows a disclosure `AlertDialog` first (Play "prominent disclosure"); on confirm
  it calls `nextBackgroundLocationStep(...)` and routes: `RequestForegroundFirst` →
  foreground-permission launcher (then continues); `RequestBackgroundInline` →
  `ACCESS_BACKGROUND_LOCATION` launcher (API 29); `DirectToSystemSettings` → opens
  `ACTION_APPLICATION_DETAILS_SETTINGS` for the package (API 30+ "Allow all the time").
- Toggling off shows a short dialog and opens system settings (can't revoke programmatically).
- Launchers wired via `rememberLauncherForActivityResult` inside the composable.

**`strings.xml`:** added German strings for the section heading, toggle label/description,
disclosure dialog (title/body/confirm/cancel), and the revoke dialog (title/body/open-settings).

### Notes / not done
- No change needed in `WidgetUpdateWorker`, `WeatherRepository`, or `LocationService`: once
  `ACCESS_BACKGROUND_LOCATION` is granted, the worker's existing `getCurrentLocation()` call
  returns a real fix and the existing `shouldFetchNewData` / day-change logic relocates the
  cache on its own (subject to Doze throttling location to a few fixes/hour, fine for a 30-min
  widget refresh). The stale stored-coords fallback stays as the offline last resort.
- The Activity wiring (dialogs, launchers, system-settings routing) has no DI seam (same
  constraint noted for `MainActivity`/widget code), so it is covered by compile + manual run,
  not unit tests. The trickiest piece — the permission-step routing — is extracted into the
  pure `nextBackgroundLocationStep` and unit-tested.

### Test results
`:app:testDebugUnitTest` — BUILD SUCCESSFUL. 65 tests run, 65 passed (0 failures).

## Issue #19 — Wind data flows into the forecast

### Status: COMPLETE

### Parent
#18 — Wind widget (1x1). This is Slice 1 of 2 (data path + direction math);
Slice 2 (#20) builds the 1x1 WindWidget on top of it.

### What was implemented

**`OpenMeteoApi.kt`:**
- Extended the default `hourly` query from `uv_index,temperature_2m` to
  `uv_index,temperature_2m,windspeed_10m,winddirection_10m`. Open-Meteo's default
  `windspeed_unit` is `kmh`, so no unit param is needed — the issue's "km/h" is the default.

**`WeatherResponse.kt` (`HourlyData`):**
- Added `@SerialName("windspeed_10m") windSpeed: List<Double> = emptyList()` and
  `@SerialName("winddirection_10m") windDirection: List<Double> = emptyList()`. Defaulted to
  empty so a partial/legacy API response without the fields still deserializes.

**`UVForecast.kt` (`HourlyForecast`):**
- Added `windSpeed: Double = 0.0` (km/h, rounded) and `windDirection: Double = 0.0`
  (source bearing in degrees — where the wind comes FROM). **Defaults are load-bearing**:
  `CachedWeatherData` serializes `UVForecast`, so old cached payloads written before this
  change still deserialize (the back-compat acceptance criterion).

**`WeatherRepository.parseWeatherResponse()`:**
- Populates the two new fields per hour: `windSpeed` via
  `response.hourly.windSpeed.getOrNull(index)?.roundToInt()?.toDouble() ?: 0.0` (rounded at
  parse time, same pattern as uv/temperature from #10/#15), `windDirection` via
  `response.hourly.windDirection.getOrNull(index) ?: 0.0` (kept raw; bucketed to an octant by
  the display helper, so no rounding needed). `getOrNull` guards against the empty-list default.
- `reParseWithCurrentTime()` needed no change — it copies `HourlyForecast` objects straight
  from `allDayForecasts`, so wind survives the cache re-parse for free.

**New pure module `com.uvindex.app.wind.WindDirection`
(`app/src/main/java/com/uvindex/app/wind/WindDirection.kt`):**
- `enum class CompassOctant { N, NE, E, SE, S, SW, W, NW }` — ordered clockwise from North;
  ordinal == 45° octant index.
- `fun travelOctant(sourceBearingDegrees: Double): CompassOctant` — converts the
  meteorological source bearing into the octant the wind travels TOWARD:
  `travel = source + 180`, normalized into `[0,360)` (handles negative / >360 inputs),
  then `(travel / 45).roundToInt() % 8` indexes `CompassOctant.entries`. So a wind "from N"
  (0°) yields a southward arrow. Pure Kotlin, no Android imports — used by Slice 2's widget.

**`WindDirectionTest.kt` (`app/src/test/java/com/uvindex/app/wind/`):**
- 11 pure JVM tests: 4 cardinal sources (N→S, E→W, S→N, W→E), 2 intercardinal (NE→SW, SW→NE),
  2 rounding-boundary cases (22°→S, 23°→SW), and 3 normalization cases (350° wrap, exactly
  360°, negative −90°).

### Notes / not done
- Wind speed/direction parsing inside `parseWeatherResponse` is not independently unit-tested:

  #15/#10). The direction math — the actual risk in this slice — is fully covered by the pure
